# Implementation Plan

> Requirement ID mapping rule for this plan: `N.M` means "Requirement N の Acceptance Criteria M" (例: `1.2` は Requirement 1 の AC2)。

- [ ] 1. Foundation: 契約と保存方針の前提を固定する
- [ ] 1.1 分析結果と根拠資料レジストリの契約型を確定する
  - 根拠資料登録、主張-出典リンク、根拠不足アラートを表現する型を定義し、既存分析結果との後方互換ルールを明文化する。
  - 参照箇所候補の確度表現（推定フラグを含む）を統一し、全処理が同じ契約を利用できる状態にする。
  - 完了条件: 拡張契約を使って型エラーなくビルドでき、既存の分析レスポンス利用箇所が破綻しない。
  - _Requirements: 1.3, 2.4, 3.1, 3.2, 3.3, 3.4, 4.1, 4.2, 4.3, 4.4_
- [ ] 1.2 MVP の保存責務を localStorage 主体に固定し、登録結果契約を定義する
  - 登録資料は UI 側で保持する方針を前提に、登録・更新・無効化・一覧取得の入出力と状態遷移を確定する。
  - 将来 API 保存へ移行するための拡張余地は残すが、本タスクでは追加 API 実装を必須にしない。
  - 完了条件: 登録処理の成功/失敗理由コードが一意に返せる契約があり、実装者が解釈を迷わない。
  - _Requirements: 1.1, 1.3, 1.4_
- [ ] 1.3 参照不能判定ポリシーを独立定義する
  - URL 正規化、重複判定、参照不能判定の優先順と失敗時の取り扱いを整理する。
  - 参照不能時の利用者通知文言に必要な理由カテゴリを固定する。
  - 完了条件: 重複と参照不能が別理由で識別され、UI 側表示に直接使える状態になる。
  - _Requirements: 1.2_

- [ ] 2. Core: 根拠資料レジストリと主張別照合ロジックを実装する
- [ ] 2.1 根拠資料レジストリの登録・更新・無効化を実装する
  - 登録時に必須項目検証、重複検出、資料状態管理を行う。
  - 無効化した資料が以後の検索対象から除外されるようにする。
  - 完了条件: 利用者が資料を登録/更新/無効化すると一覧状態が即時反映される。
  - _Requirements: 1.1, 1.2, 1.3, 1.4_
- [ ] 2.2 (P) 主張ごとの関連資料スコアリングを実装する
  - シード資料と登録資料を統合し、主張単位で候補を関連度順に返す。
  - 候補がない主張を明示できる戻り値形状を提供する。
  - 完了条件: 同一入力で主張ごとの候補順が再現可能に得られ、候補ゼロ主張が判別できる。
  - _Requirements: 2.1, 2.2, 2.3, 2.4_
  - _Boundary: EvidenceMatcher_
- [ ] 2.3 (P) 参照箇所候補と確度判定を実装する
  - 主張と資料候補から参照箇所候補を抽出し、確度に応じて推定フラグを付与する。
  - 確度不足時に再確認を促すための情報を結果へ含める。
  - 完了条件: 参照箇所候補に確度情報が付き、低確度時は推定扱いで返る。
  - _Requirements: 3.1, 3.2_
  - _Boundary: CitationLocator_
- [ ] 2.4 (P) 根拠不足アラートと優先度算出を実装する
  - 候補ゼロ、低確度のみ、無効資料のみの主張を根拠不足として判定する。
  - 記事内で優先確認順を識別できる優先度を算出する。
  - 完了条件: 複数主張で根拠不足が発生した際に優先度付きアラートが返る。
  - _Requirements: 2.3, 4.1, 4.2, 4.4_
  - _Boundary: EvidenceGapEvaluator_

- [ ] 3. Integration: API・UI・メモ生成へ統合する
- [ ] 3.1 分析オーケストレーションへ照合/参照箇所/アラートを統合する
  - 主張抽出から資料候補、参照箇所、根拠不足判定までを一連の分析結果として組み立てる。
  - 編集メモに主張-出典対応と追加確認ガイダンスを反映する。
  - 完了条件: 1回の分析レスポンスで主張別出典、参照箇所、根拠不足情報、メモが一貫して得られる。
  - _Depends: 2.2, 2.3, 2.4_
  - _Requirements: 2.1, 2.3, 2.4, 3.1, 3.3, 3.4, 4.1, 4.3, 4.4_
- [ ] 3.2 分析 API の入出力検証とエラー応答を更新する
  - 拡張契約の入力検証を維持し、契約外フィールドを返さない応答整形を行う。
  - 登録/分析失敗時に利用者が修正行動を取れるエラー情報を返す。
  - 完了条件: API 応答が拡張契約に一致し、入力不備や処理失敗が理由付きで返る。
  - _Depends: 1.1, 1.2, 1.3, 3.1_
  - _Requirements: 1.2, 2.4, 3.3, 4.1, 4.3_
- [ ] 3.3 UI に資料登録導線と主張別根拠表示を統合する
  - 分析画面で資料登録/無効化操作を行えるようにし、主張ごとの出典と参照箇所を表示する。
  - 根拠不足アラートと優先確認対象を視覚的に区別して提示する。
  - 完了条件: 利用者が単一画面で登録→分析→根拠確認→編集判断まで実行できる。
  - _Depends: 2.1, 3.1, 3.2_
  - _Requirements: 1.1, 1.4, 2.1, 2.4, 3.2, 3.3, 4.1, 4.2, 4.3_

- [ ] 4. Validation: 受け入れ基準に対する検証を実施する
- [ ] 4.1 登録・照合・アラートのユニットテストを実装する
  - 重複判定、参照不能判定、関連度順、低確度フラグ、優先度算出を個別に検証する。
  - 完了条件: 主要判定ロジックのテストが再現可能に通過し、要件対応を確認できる。
  - _Requirements: 1.2, 2.2, 3.2, 4.2, 4.4_
- [ ] 4.2 分析 API 統合テストを実装する
  - 登録資料の反映、候補ゼロ時のアラート、主張-出典紐づけを API レベルで検証する。
  - 完了条件: 分析 API が拡張契約どおりの JSON を返し、主要異常ケースの応答が確認できる。
  - _Requirements: 1.1, 1.4, 2.1, 2.3, 3.1, 3.3, 4.1, 4.3_
- [ ] 4.3 UI/E2E 受け入れ検証を実施する
  - 記事入力から資料登録、分析実行、主張別根拠確認、根拠不足アラート確認までの導線を検証する。
  - 完了条件: 編集者視点の主要フローが単一画面で完了し、要件に反する表示崩れや欠落がない。
  - _Requirements: 1.1, 2.1, 2.4, 3.3, 4.1, 4.2, 4.3_
