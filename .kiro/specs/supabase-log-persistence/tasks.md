# Implementation Plan

> Requirement ID mapping rule for this plan: `N.M` は「Requirement N の Acceptance Criteria M」を示す。

- [ ] 1. Foundation: Supabase ログ永続化の実行前提を整える
- [ ] 1.1 Supabase クライアント初期化と設定不足検知を実装する
  - サーバ側でプロジェクト URL と anon key の存在を検証し、欠落時に `CONFIG_MISSING` を返せる初期化層を作る。
  - 特権鍵をクライアント配信経路で参照しない制約を明示する。
  - 完了条件: 設定不足環境でログ API が同一エラー形式を返し、設定済み環境ではクライアント生成に成功する。
  - _Requirements: 7.1, 7.2_
- [ ] 1.2 `ResearchLog` と DB row の双方向マッピング契約を実装する
  - `timestamp` と `created_at` の差分を吸収する変換を定義し、snake_case フィールドを欠落なく扱う。
  - スキーマ不整合時に `SCHEMA_MISMATCH` として検知できる判定を組み込む。
  - 完了条件: 変換処理のみで `ResearchLog` 全項目の round-trip が成立する。
  - _Requirements: 8.1, 8.2, 8.3, 8.4_
- [ ] 1.3 Supabase 共有テーブルとアクセス制御をセットアップする
  - `fact_check_sessions` テーブルと RLS/公開アクセス方針を要件どおり適用する。
  - 共有モデルでの保存・取得・全削除を阻害しない最小設定を確認する。
  - 完了条件: セットアップ済み環境で create/read/delete-all 操作が成立する。
  - _Requirements: 4.2, 4.3, 7.3_
- [ ] 1.4 API 共通エラー封筒ルールを確定する
  - `CONFIG_MISSING`、`DB_UNAVAILABLE`、`SCHEMA_MISMATCH`、`DELETE_CONFIRMATION_REQUIRED` の返却形式を統一する。
  - 完了条件: 各 API ハンドラが同じエラー封筒を再利用できる。
  - _Requirements: 1.3, 2.4, 6.6, 7.1, 8.4_

- [ ] 2. Core: ログ API と永続化機能を実装する
- [ ] 2.1 `ResearchLogRepository` に保存・取得・全削除を実装する
  - 保存、created_at 降順取得、全件削除を単一境界で提供する。
  - 全削除は確認語句が `DELETE` の場合のみ実行対象にする。
  - 完了条件: Repository 単体で create/list/purgeAll の成功・失敗を判別できる。
  - _Depends: 1.1, 1.2, 1.4_
  - _Requirements: 1.1, 2.3, 4.3, 6.2, 6.3, 8.1, 8.2_
- [ ] 2.2 `/api/research-logs` の GET/POST/DELETE 契約を実装する
  - GET は新しい順で `ResearchLog[]` を返し、POST は作成レコード、DELETE は削除件数を返す。
  - 入力不備・設定不足・DB失敗・確認語句不一致時に共通エラー封筒を返す。
  - 完了条件: API 契約の正常系/異常系が単一エンドポイントで一貫する。
  - _Depends: 1.1, 1.4, 2.1_
  - _Requirements: 1.1, 1.3, 2.1, 2.4, 4.1, 6.2, 6.3, 6.6, 7.1_

- [ ] 3. Integration: UI と既存集計機能を Supabase 経由に統合する
- [ ] 3.1 初期ログロードと一覧表示を API 取得へ置換する
  - 起動時に Supabase ログを取得し、Logs タブを新しい順で描画する。
  - 取得失敗時の通知と再試行導線を追加する。
  - 完了条件: 起動直後に共有ログが表示され、失敗時も再試行操作が可能になる。
  - _Depends: 2.2_
  - _Requirements: 2.1, 2.3, 2.4, 4.1, 5.2, 5.4_
- [ ] 3.2 ダッシュボード集計とサイドバー指標を API ログ連動へ切り替える
  - セッション数、平均信頼性、リスク件数、評価平均、理由分布、トピック分布を API ログ起点で再計算する。
  - 完了条件: 画面内の全メトリクスが同一ログデータに同期して更新される。
  - _Depends: 3.1_
  - _Requirements: 2.1, 2.5_
- [ ] 3.3 ログ保存操作を API POST へ置換し成功時 UI 更新を統合する
  - 保存成功時に先頭追加と入力リセット、失敗時に入力保持を実装する。
  - 同一操作で重複保存を防ぎ、再送操作が成立する状態を維持する。
  - 完了条件: 「ログを保存」1回で1件のみ作成され、失敗時は入力が保持される。
  - _Depends: 2.2, 3.2_
  - _Requirements: 1.2, 1.3, 1.4, 2.5, 5.1_
- [ ] 3.4 全件削除ダイアログと DELETE 実行フローを統合する
  - 件数、全ユーザー対象、取消不能を示す確認ダイアログを表示する。
  - `DELETE` 一致時のみ削除実行し、0件時はボタン無効化する。
  - 完了条件: ダイアログ条件を満たした時だけ削除が成立し、成功後に一覧と集計が空状態になる。
  - _Depends: 2.2, 3.1, 3.2_
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6_
- [ ] 3.5 CSV エクスポートと契約同期ルールを維持する
  - API 取得ログを既存 CSV 仕様（ヘッダ順・配列 `;` 連結）で出力する。
  - 0件時無効化と、契約変更時の同期ポイント（types/csv/schema）を実装規約に反映する。
  - 完了条件: Supabase ログを既存形式 CSV として出力でき、0件時は押下不能になる。
  - _Depends: 3.1_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 8.2_
- [ ] 3.6 `localStorage` 永続化経路を完全に撤去する
  - `climate-studio-logs` への read/write と移行処理を削除する。
  - 既存ブラウザ残存データを参照しないことを明示する。
  - 完了条件: ログ機能が `localStorage` API なしで動作し、残存キーが表示に影響しない。
  - _Depends: 3.1, 3.3_
  - _Requirements: 5.1, 5.2, 5.3, 5.4_

- [ ] 4. Validation: 受け入れ基準に対する検証を実装する
- [ ] 4.1 Repository とマッピングの単体テストを実装する
  - 保存/取得/削除、`timestamp`↔`created_at` 変換、`SCHEMA_MISMATCH` を検証する。
  - 完了条件: 契約変換と削除ガードの単体テストが安定して通過する。
  - _Requirements: 6.2, 6.3, 8.1, 8.2, 8.3, 8.4_
- [ ] 4.2 API 統合テストを実装する
  - GET/POST/DELETE の正常系と設定不足・確認語句不一致・DB失敗を検証する。
  - 完了条件: ログ API の主要成功/失敗パターンが契約どおりであることを確認できる。
  - _Requirements: 1.1, 1.3, 2.1, 2.4, 6.2, 6.3, 6.6, 7.1_
- [ ] 4.3 UI/E2E 検証を実装する
  - 起動時取得、保存、CSV、全件削除確認ダイアログ、失敗時状態保持を検証する。
  - 完了条件: 主要ユーザーフローが単一画面で成立し、要件に反する欠落がない。
  - _Requirements: 1.2, 2.1, 2.2, 3.1, 3.3, 6.1, 6.4, 6.5_
