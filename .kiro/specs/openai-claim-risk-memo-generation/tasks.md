# Implementation Plan

- [x] 1. Foundation: OpenAI 連携の基盤設定と契約準備
- [x] 1.1 OpenAI SDK と環境変数の実行前提を整備する
  - OpenAI クライアント利用に必要な依存関係と設定読み込み方針を追加し、開発環境で安全に初期化できるようにする。
  - API キー未設定時の挙動（起動時または実行時の明確な失敗）を定義する。
  - 完了条件: API キー有無で挙動が分かれ、未設定時に原因が判別できるエラーが再現する。
  - _Requirements: 4.2_
- [x] 1.2 構造化出力とエラー封筒の型契約を定義する
  - 既存 `AnalysisResult` 互換を維持しつつ、OpenAI 応答の中間構造とエラー分類型を追加する。
  - UI 側が利用する成功/失敗レスポンスの契約面を明文化する。
  - 完了条件: 型チェックで `AnalysisRequest` 入力と `AnalysisResult` 互換出力、エラー封筒の整合が取れる。
  - _Requirements: 4.1, 4.2, 4.4_

- [x] 2. Core: OpenAI 解析コンポーネントを実装する
- [x] 2.1 (P) OpenAI 呼び出しアダプタと再試行制御を実装する
  - OpenAI Responses API 呼び出しを担当するアダプタを実装し、429/timeout/5xx に対する再試行戦略を組み込む。
  - 拒否応答や不完全応答を上位で扱える正規化エラーへ変換する。
  - 完了条件: 正常応答・再試行成功・再試行失敗の3系統が判別可能な戻り値として観測できる。
  - _Requirements: 1.1, 4.1, 4.2_
  - _Boundary: OpenAIAdapter_
- [x] 2.2 (P) 構造化出力スキーマと応答検証ロジックを実装する
  - 主張・リスク・根拠確認ポイント・編集支援メモを含む構造化出力スキーマを定義する。
  - 応答が契約外の場合に検証エラーとして扱えるようにする。
  - 完了条件: 契約準拠データは通過し、契約違反データは検証失敗として検出される。
  - _Requirements: 1.4, 2.1, 2.2, 3.1, 4.1_
  - _Boundary: schema_
- [x] 2.3 (P) プロンプト生成とドメインマッピングを実装する
  - 入力文脈から主張抽出・リスク指摘・根拠確認ポイント・表現緩和提案を誘導するプロンプト生成を実装する。
  - OpenAI 応答を UI 互換の `AnalysisResult` に変換し、重複統合や主張なしケースを処理する。
  - 完了条件: 入力例に対して重複統合済み主張、リスク、編集メモが `AnalysisResult` 形式で得られる。
  - _Requirements: 1.2, 1.3, 2.3, 2.4, 3.2, 3.4_
  - _Boundary: prompts, mapper_

- [x] 3. Integration: 既存解析経路に統合し UI 契約を維持する
- [x] 3.1 `lib/analysis` を OpenAI オーケストレーションへ移行する
  - 既存公開入口を維持しながら、OpenAI アダプタ・スキーマ検証・マッピングを接続する。
  - ルールベース実装の責務を置換し、成功時出力の後方互換を担保する。
  - 完了条件: 既存の分析実行導線で `AnalysisResult` が返り、主要表示項目が維持される。
  - _Requirements: 1.1, 1.4, 2.1, 3.1, 4.1, 4.4_
  - _Depends: 1.2, 2.1, 2.2, 2.3_
- [x] 3.2 `app/api/analyze` のエラー分類レスポンスを実装する
  - 入力不備、再試行可能エラー、再試行困難エラーを区別して API 応答を返す。
  - UI が再試行判断しやすいエラーメッセージ情報を含める。
  - 完了条件: 失敗ケースごとに HTTP ステータスとエラー本文が一貫して返る。
  - _Requirements: 4.2, 4.4_
  - _Depends: 2.1, 3.1_
- [x] 3.3 `StudioApp` 側の失敗時表示と既存評価導線の互換を確認・調整する
  - API エラー時に利用者へ再試行/入力見直しを促せる表示を追加または調整する。
  - 分析成功時の表示と評価入力導線が維持されることを確認する。
  - 完了条件: 成功・失敗の両ケースで画面遷移なしに次アクションを判断できる。
  - _Requirements: 3.3, 4.2, 4.3_
  - _Depends: 3.2_

- [x] 4. Validation: 要件適合テストと品質確認を実施する
- [x] 4.1 構造化出力と主張抽出品質のユニットテストを追加する
  - 重複主張統合、主張なし分岐、主要4リスク識別、メモ生成要件を対象にテストを整備する。
  - 完了条件: 想定入力に対する主張・リスク・メモの契約がテストで再現可能になる。
  - _Requirements: 1.2, 1.3, 2.2, 3.1, 3.2, 3.4_
- [x] 4.2 API 統合テストで正常系・異常系を検証する
  - `/api/analyze` で正常返却、入力不備、外部障害時エラー分類を検証する。
  - 完了条件: API 層の主要分岐がテストで網羅され、利用者判断に必要なエラー情報が確認できる。
  - _Requirements: 1.1, 4.1, 4.2, 4.4_
- [x] 4.3 E2E 観点で既存評価フロー互換を確認する
  - 入力→分析→結果確認→評価記録までの一連フローを確認する。
  - エラー表示時の再試行導線と、成功時の既存評価導線継続を確認する。
  - 完了条件: 主要ユーザーフローが破綻なく完了し、仕様上の隣接期待が満たされる。
  - _Requirements: 3.3, 4.2, 4.3_
